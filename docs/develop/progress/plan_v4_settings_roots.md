# Image Triage v4 - Settings-Centered Root Management

**Status:** `[x]` complete
**Created:** 2026-11-13
**Supersedes:** the remaining GUI setup flow from [`plan_v2_gui_workflow`](plan_v2_gui_workflow.md). The multi-root data model and workflow from [`plan_v3_multi_root_library`](plan_v3_multi_root_library.md) remain authoritative.
**Target:** make the Settings page the single place to manage watched roots and the central state database, and remove the obsolete, misleading Setup page.

---

## 1. Objective and desired outcome

The v3 GUI still exposes a legacy `/setup` page. It changes only the in-memory `input.root`, ignores the configured `input.roots`, is not persisted, and claims that the state database lives inside the selected photo folder. In a v3 installation with `input.roots` configured, the page has no effect on the library.

The settings page must become the authoritative root manager:

1. list every configured watched root with an active checkbox, image counts and a remove action;
2. add a root by path or through a server-side directory browser;
3. show the central state database path as read-only information;
4. keep all existing settings, but present them in clearly separated sections;
5. remove the Setup page and redirect old bookmarks to Settings.

The change must remain local-first, deterministic and non-destructive. Removing a root must never delete originals, database history or ratings.

---

## 2. Scope, constraints and explicit non-goals

### 2.1 In scope

- Settings model support for active and inactive watched roots.
- Repository synchronisation of root state with the central `roots` table.
- Settings page root table: active checkbox, path, on-disk image count, analyzed count and remove button.
- Add-root form with a server-side directory browser.
- Read-only database location display.
- Cleaner settings-page structure and styling.
- Removal of the `/setup` route, template and navigation entry.
- Tests and documentation for the new behavior.

### 2.2 Constraints

- Local-only, single-user, no authentication.
- Originals are never modified or deleted.
- Removing a root does not delete `photo_locations`, `photos`, ratings or overrides; it only removes the root from the configured list and disables it in the database.
- The central database path is displayed read-only. No database move or replacement is performed by the GUI.
- The CLI and GUI continue to share the central YAML configuration.
- `config.yaml` and `docs/usage/config.md` are generated by `make syncdocs`; never edit them directly.
- The full repository gate (`make fmt`, `make lint`, `make test`) must pass.

### 2.3 Explicit non-goals

- No database relocation, copy or deletion UI.
- No destructive purge of root data from the database.
- No live filesystem watching or automatic rescanning.
- No cloud or multi-user support.
- No new heavyweight UI framework.

## 3. Architecture and decisions

### 3.1 Settled product decisions

| Area | Decision |
| --- | --- |
| Setup page | Remove it; redirect `/setup` to `/settings` for old bookmarks. |
| Watched roots | `input.roots` remains the configured list; `input.disabled_roots` stores inactive entries. |
| Active state | `Settings.watched_roots` returns configured roots minus disabled roots. |
| Legacy fallback | `input.root` remains a fallback only when no `input.roots` are configured. |
| Root removal | Remove from `input.roots` and disable in the database. Keep history and originals. |
| Root statistics | Show on-disk image count and analyzed location count per root. |
| Directory browser | Server endpoint listing directories under a path; no browser upload. |
| Database location | Read-only display of `Settings.database_path`; no edit, move or replacement. |
| Settings layout | Grouped sections with a root table, add form, directory dialog and sticky save action. |
| Job guard | Root and settings changes remain blocked while a job is active. |

### 3.2 Settings model

`InputSettings` gains:

- `disabled_roots: list[Path]`, defaulting to an empty list.

`Settings.watched_roots`:

- resolves and de-duplicates `input.roots`;
- removes entries whose resolved path is in `disabled_roots`;
- falls back to `input.root` only when no configured roots exist.

### 3.3 Repository root state

`Repository.sync_roots()` accepts an optional `enabled` subset:

- it ensures every supplied root exists;
- it marks exactly the enabled subset as enabled and all other roots as disabled;
- existing analysis history is retained.

The GUI settings save calls it with all configured roots and the active subset.

### 3.4 Settings page behavior

`GET /settings` provides:

- all configured roots with `path`, `exists`, `enabled`, `disk_images` and `analyzed`;
- excluded directory names;
- the central database path;
- the existing display, export, blur, scoring and analysis settings.

`POST /settings` accepts:

- repeated `root_paths` fields, preserving the current order;
- repeated `enabled_roots` checkbox values;
- an optional `new_root` path;
- optional action fields for add and remove;
- the existing settings fields.

Validation:

- at least one active root is required;
- active roots must be existing directories;
- duplicate roots are rejected or de-duplicated deterministically;
- an invalid root or database change returns the settings page with an inline error;
- changes are rejected while a job is active.

### 3.5 Directory browser

`GET /api/browse?path=...`:

- expands `~` and resolves the path;
- rejects missing paths and regular files;
- returns the current path, parent path and sorted subdirectories;
- is used by a small modal in the settings page to fill the new-root input.

### 3.6 Database location

The settings page displays `Settings.database_path` and whether it is the platform default or an explicit `input.db_path` override. It is read-only; the page explains that the database is central and shared by all roots.

## 5. Acceptance criteria

- `/setup` no longer renders a setup form and redirects to `/settings`.
- The Settings page lists every configured root with an active checkbox, image counts and a remove button.
- A root can be added by path or through the directory browser.
- A root can be deactivated, reactivated and removed without deleting originals or analysis history.
- The database path is visible and read-only.
- At least one active root is enforced.
- Root changes are rejected while a job is active.
- `make fmt`, `make lint` and `make test` pass.
- `docs/usage/gui.md`, `config.yaml` and `docs/usage/config.md` agree with the implementation.

---

## 6. Risks and open questions

- **Directory count cost.** Counting images recursively can be expensive on very large roots. The settings page computes the counts directly for now; a cache can be added if loading becomes slow.
- **Root history visibility.** Removed roots disappear from the configured list but remain in the database as disabled roots. This is intentional and documented.
- **No open questions.** The database path is read-only, removal is non-destructive, both count types are shown and at least one active root is required.
